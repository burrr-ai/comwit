# 계층보다 도메인을 중심에 두는 이유

첫날은 언제나 괜찮습니다. 사람이든 모델이든 몇 분이면 CRUD 페이지의 뼈대를 만들 수 있습니다. 진짜 시험은 몇 달 뒤에 옵니다. 기능이 마흔 개쯤 생긴 뒤 제품 관리자가 방향을 바꾸고, 좋아요 버튼 하나 때문에 폴더 네 곳의 파일 열두 개를 고쳐야 합니다. 다른 기능 세 개가 의존하는 공유 utils 폴더에 왜 `formatCount`가 있는지 아무도 기억하지 못합니다.

이 템플릿은 그런 방식으로 여러 제품을 만들며 도달한 답입니다. 새로운 답은 아닙니다. Redux slices, Feature-Sliced Design, 수직 슬라이스 아키텍처도 같은 결론에 이릅니다. 여기서는 그 답을 모든 폴더, 모든 린트 규칙, 모든 `.ai.md`에 반영했습니다.

<a id="three-traps"></a>

## 세 가지 함정

성장하는 거의 모든 React 프로젝트에서 나타납니다.

**비슷한 UI를 지나치게 추상화하기.** `PostCard`와 `ProductCard`가 비슷해 보이니 누군가 `variant="post"`와 `variant="product"`를 받는 공유 `CardView`를 만듭니다. 6개월 뒤에는 속성 열네 개와 조건 분기 세 개가 생기고, 게시물 레이아웃을 고치다 상품 페이지가 깨질까 봐 아무도 손대지 않습니다. 비슷해 보인다고 같은 것은 아닙니다. 게시물 카드와 상품 카드는 완전히 다른 비즈니스 이유로 바뀝니다.

**관심사를 지나치게 분리하기.** API는 팔로워 수를 `1234567`로 반환하지만 UI는 `1.2M`이 필요하므로 모든 곳에서 `formatFollowerCount` 유틸리티를 호출합니다. 제품 요구사항에 마우스를 올리면 정확한 숫자를 보여 달라는 요청이 오면 컴포넌트 여덟 개를 찾아다녀야 합니다. 값이 컴포넌트에 도착하기 전에 데이터 계층에서 한 번 포맷하세요.

**응집된 작업을 지나치게 나누기.** 게시물 좋아요는 목록 항목 갱신, 상세 화면 갱신, 요청 전송, 오류 처리를 뜻합니다. 단일 책임이라는 명목으로 함수 네 개로 나누면 다음 작업자가 하나를 빠뜨립니다. 함께 일어나는 작업은 함께 두어야 합니다.

<a id="the-real-villain-is-change"></a>

## 진짜 어려움은 변경

요구사항이 바뀌지 않는다면 어떤 구조라도 괜찮습니다. 하지만 요구사항은 늘 바뀌며, 이는 과정의 결함이 아니라 우리가 하는 일입니다. 유용한 질문은 완벽한 코드를 작성하는 방법보다 변경 비용을 낮추는 방법입니다.

실제 요구사항은 **도메인 단위**로 들어옵니다. 게시물 태그 추가는 post 도메인입니다. 사용자 프로필 사진은 user 도메인입니다. 장바구니 할인 코드는 cart 도메인입니다. 누구도 `formatDate`를 쓰는 모든 컴포넌트를 바꾸라고 요청하지 않습니다.

변경은 도메인별로 전파되고 내용도 도메인마다 다릅니다. 코드도 같은 방식으로 나누어야 합니다.

<a id="slicing"></a>

## 나누기

기술적 역할별로 묶는 대신:

```text
src/
  components/  PostCard.tsx   UserAvatar.tsx   CartItem.tsx
  hooks/       usePost.ts     useUser.ts       useCart.ts
  api/         post.ts        user.ts          cart.ts
```

비즈니스 단위로 묶고 그 안에 기술 계층을 두세요.

```text
src/services/app/
  api/    post/   user/   cart/
  state/  post/   user/   cart/
  page/   posts/  profile/  cart/
```

게시물에 댓글을 추가하라는 요구가 오면 각 계층의 `post` 슬라이스를 열었을 때 필요한 것이 모두 있습니다. 코드가 `components/`, `hooks/`, `api/`, `store/` 전반에 흩어지지 않습니다.

계층은 여전히 존재합니다. 서버 액션, 클라이언트 상태, React는 서로 다른 책임과 런타임을 가지기 때문입니다. 다만 최상위 구조는 계층이 아니라 도메인이 결정합니다.

<a id="rules-that-came-from-doing-this"></a>

## 실제 경험에서 나온 규칙

템플릿은 다음 규칙을 강제하며 각각은 위 함정에 대한 해결책입니다.

- **페이지는 어떤 도메인이든 조합합니다.** 페이지는 조합 계층으로 필요에 따라 `post`, `user`, `cart`를 가져옵니다.
- **도메인 UI는 공유하지 않고 반복합니다.** 두 페이지에서 게시물 카드를 표시하면 게시물 카드 컴포넌트도 두 개입니다. UI는 반복하고 로직은 재사용합니다.
- **도메인 상태는 전역입니다.** 도메인마다 어디에서나 접근 가능한 스토어 하나를 둡니다. prop drilling이나 도메인별 컨텍스트 프로바이더가 필요하지 않습니다.
- **목록과 상세를 함께 둡니다.** 모델을 공유하므로 목록에서 게시물에 좋아요를 누르면 상세 화면도 갱신됩니다.
- **액션은 상태를 압니다.** 게시물 상세 페이지의 액션은 현재 게시물을 이미 알고 있으므로 UI가 `postId`를 전달하지 않습니다.
- **API 계층에서 전처리합니다.** 컴포넌트에 도착하기 전에 원시 숫자는 `1.2M`으로, 타임스탬프는 `3 days ago`로 바뀝니다. 컴포넌트는 포맷, 필터링, 집계, 슬라이스를 하지 않습니다.
- **도메인 객체는 통째로 전달합니다.** 수많은 스칼라 속성 대신 `<PostCard post={post} />`를 사용합니다.
- **의존성은 한 방향으로 흐릅니다.** `page → state → api → repository`. 역방향이나 우회는 허용하지 않으며 페이지는 api를 직접 호출하지 않습니다.

<a id="two-kinds-of-slice"></a>

## 두 종류의 슬라이스

도메인은 비즈니스 객체별로 나눕니다. **서비스**는 사용자 유형별로 나눕니다. 템플릿은 최종 사용자용 `app`과 운영자용 `admin`으로 시작하며 각각 자체 레이아웃, 인증 경계, UI를 가집니다. 서비스 간 교차 import는 금지하고 공유 코드는 `src/lib`와 `src/server`에 둡니다. 구매자와 별도로 공급자처럼 실제로 다른 사용자 유형을 제공하는 제품이라면 모든 화면에서 분기하는 대신 세 번째 서비스를 추가합니다.

<a id="why-this-matters-more-with-ai"></a>

## AI와 함께할 때 더 중요한 이유

모델에게 게시물 북마크 기능을 추가해 달라고 하면 먼저 코드베이스를 이해해야 합니다. 역할별로 묶인 프로젝트에서는 게시물 동작을 파악하려고 `components/`, `hooks/`, `api/`, `store/`를 두루 읽다가 일부를 놓치거나 코드를 잘못된 곳에 넣습니다.

도메인 슬라이스에서는 `state/post/types.ts`를 읽으면 도메인이 무엇을 관리하고 어떤 액션이 있으며 각 액션이 무엇을 하는지 알 수 있습니다. `model.ts`는 초기화를, `actions/*.ts`는 구현을, `index.ts`는 공개 인터페이스를 보여줍니다. 작성 순서와 의존성 방향은 항상 같고, 린트 규칙이 그 외의 방식을 거부합니다.

그래서 템플릿은 긴 README 대신 각 계층 옆에 `.ai.md`를 둡니다. 구조 자체가 문서이며 옆의 가이드는 구조만으로 표현할 수 없는 몇 가지를 설명합니다. 팀 안에만 전해지던 지식을 놓친 사람도 같은 도움을 받습니다.

좋은 아키텍처는 언제나 답이었습니다. 모델은 이를 무시하는 비용을 더 이상 숨길 수 없게 만들었을 뿐입니다.
