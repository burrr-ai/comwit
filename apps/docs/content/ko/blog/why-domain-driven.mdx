<a id="your-codebase-will-rot-the-question-is-how-fast"></a>

## 코드베이스는 낡습니다. 문제는 얼마나 빠르냐입니다.

첫날은 언제나 괜찮습니다. 개발자든 LLM이든 몇 분이면 CRUD 페이지의 뼈대를 만들 수 있습니다. 진짜 시험은 6개월 뒤입니다. 기능은 40개, 개발자 세 명은 떠났고 제품 관리자는 또 방향을 바꿨습니다.

잘못된 아키텍처는 초반에 문제를 드러내지 않습니다. 90일쯤 지나 단순한 좋아요 버튼 하나 때문에 디렉터리 네 곳의 파일 열두 개를 고쳐야 할 때 문제가 됩니다. 다른 기능 세 개가 의존하는 공유 utils 폴더에 왜 `formatCount`가 있는지 아무도 기억하지 못합니다.

도메인 주도 설계가 이를 해결합니다. 그리고 AI 지원 개발을 규모가 커져도 실제로 작동하게 만드는 방법이기도 합니다.

<a id="three-traps-that-kill-your-speed"></a>

## 속도를 떨어뜨리는 세 가지 함정

가정이 아닙니다. 성장하는 거의 모든 React 프로젝트에서 나타납니다.

<a id="trap-1-over-abstracting-similar-uis"></a>

### 함정 1: 비슷한 UI를 지나치게 추상화하기

`PostCard`와 `ProductCard`가 있습니다. 비슷하게 생겼습니다. 누군가 `variant="post"`와 `variant="product"`를 받는 공유 `CardView` 컴포넌트를 만듭니다. 6개월 뒤 `CardView`에는 속성 열네 개와 조건 분기 세 개가 생겼습니다. 게시물 레이아웃을 바꾸다 상품 페이지가 깨질까 봐 아무도 손대고 싶어 하지 않습니다.

비슷한 UI의 중복을 없애고 싶은 유혹은 강합니다. 하지만 비슷해 보인다고 같은 것은 아닙니다. 게시물 카드와 상품 카드는 완전히 다른 비즈니스 이유로 바뀝니다. 우연히 텍스트가 들어 있는 직사각형일 뿐입니다.

<a id="trap-2-over-separating-concerns"></a>

### 함정 2: 관심사를 지나치게 분리하기

API가 팔로워 수를 `1234567`로 반환합니다. UI에는 “1.2M”으로 보여야 합니다. 그래서 `formatFollowerCount` 유틸리티를 만들고 모든 곳에서 호출합니다. 이제 포맷 로직이 UI 계층 전체에 흩어졌습니다. 제품 담당자가 마우스를 올리면 정확한 숫자를 보여 달라고 하면 컴포넌트 여덟 개를 찾아다녀야 합니다.

해결책은 간단합니다. 컴포넌트에 도착하기 전에 데이터 계층에서 한 번 포맷하세요.

<a id="trap-3-over-splitting-cohesive-operations"></a>

### 함정 3: 응집된 작업을 지나치게 나누기

사용자가 게시물에 좋아요를 누릅니다. 목록의 게시물 갱신, 상세 화면 갱신, API 요청, 오류 처리가 필요합니다. 단일 책임을 이유로 이를 함수 네 개로 나눕니다. 이제 사이드바의 좋아요 수도 갱신해야 하면 함수 다섯 개를 정확한 순서로 호출해야 한다는 사실을 기억해야 합니다.

누군가는 빠뜨립니다. 늘 그렇습니다.

함께 일어나는 작업은 함께 두어야 합니다.

<a id="the-real-villain-is-the-person-who-changes-their-mind"></a>

## 진짜 어려움은 바뀌는 요구사항

요구사항이 바뀌지 않는다면 어떤 코드 구조도 괜찮습니다. 스파게티 코드든 완벽한 계층이든 5,000줄짜리 파일 하나든 상관없습니다. 한 번 쓰고 다시 건드리지 않으면 됩니다.

하지만 요구사항은 늘 바뀝니다. PM이 생각을 바꾸고 디자이너가 레이아웃을 고치며 새로운 비즈니스 규칙이 갑자기 등장합니다. 과정의 결함이 아니라 바로 우리가 하는 일입니다.

따라서 중요한 질문은 완벽한 코드를 작성하는 방법보다 변경 비용을 낮추는 방법입니다.

요구사항이 실제로 어떻게 바뀌는지 보면 도메인별로 바뀝니다. 게시물 태그 추가는 post 도메인, 사용자 프로필 사진은 user 도메인, 장바구니 할인 코드는 cart 도메인입니다. 누구도 `formatDate`를 사용하는 모든 컴포넌트를 바꾸라고 말하지 않습니다.

<a id="domain-driven-slicing"></a>

## 도메인 주도 분할

핵심은 간단합니다. 기술 계층보다 비즈니스 도메인에 따라 코드를 구성하세요.

이 구조 대신:

```
src/
  components/
    PostCard.tsx
    UserAvatar.tsx
    CartItem.tsx
  hooks/
    usePost.ts
    useUser.ts
    useCart.ts
  api/
    post.ts
    user.ts
    cart.ts
```

다음 구조를 사용합니다.

```
src/
  state/
    post/
      types.ts
      model.ts
      actions/
      index.ts
    user/
      types.ts
      model.ts
      actions/
      index.ts
    cart/
      types.ts
      model.ts
      actions/
      index.ts
```

게시물에 댓글을 추가하라는 요구가 오면 `state/post/`를 열었을 때 필요한 모든 것이 있습니다. `components/`, `hooks/`, `api/`, `store/`에 변경을 흩뿌리지 않습니다.

새로운 아이디어는 아닙니다. Redux slices, Feature-Sliced Design, Vertical Slice Architecture 모두 같은 결론에 이릅니다. comwit은 도메인 경계를 라이브러리의 기본 단위로 삼아 한 걸음 더 나아갑니다.

<a id="practical-rules"></a>

### 실용적인 규칙

시행착오에서 얻었으며 실제로 효과가 있는 규칙입니다.

- **페이지는 어떤 도메인 상태든 참조할 수 있습니다.** 페이지는 조합 계층이며 필요에 따라 post, user, cart를 가져옵니다.
- **도메인 UI는 페이지 간 공유하지 않습니다.** 두 페이지에서 게시물 카드를 보여주면 게시물 카드 컴포넌트도 두 개입니다. UI는 반복하고 로직은 재사용합니다.
- **도메인 상태는 항상 전역입니다.** prop drilling이나 도메인별 컨텍스트 프로바이더 없이 어디서나 접근 가능한 도메인별 스토어 하나를 둡니다.
- **목록과 상세는 함께 관리합니다.** 목록에서 게시물에 좋아요를 누르면 상세도 갱신되어야 합니다. 같은 모델을 공유합니다.
- **액션은 상태를 압니다.** 게시물 상세 페이지라면 액션이 현재 게시물을 이미 알고 있으므로 UI에서 `postId`를 전달할 필요가 없습니다.
- **API 계층에서 데이터를 전처리합니다.** 원시 숫자는 “1.2M”, 타임스탬프는 “3 days ago”가 됩니다. 컴포넌트는 포맷하지 않습니다.
- **도메인 객체는 통째로 전달합니다.** `<PostCard title={post.title} date={post.date} author={post.author} />` 대신 `<PostCard post={post} />`를 사용합니다.
- **의존성은 한 방향으로 흐릅니다.** 페이지는 state에, state는 API에 의존하며 역방향은 허용하지 않습니다.

<a id="how-comwit-is-built-around-this"></a>

## comwit이 이 원칙을 바탕으로 만들어진 방식

나중에 도메인 주도 설계를 덧붙인 것이 아닙니다. 라이브러리 전체가 이 원칙으로 구성됩니다. 모든 도메인은 같은 파일 구조를 따르고 API는 이 패턴을 가장 자연스럽게 사용할 수 있도록 설계되었습니다.

<a id="typests--the-domain-contract"></a>

### types.ts — 도메인 계약

모든 도메인은 여기서 시작합니다. 상태 구조와 사용 가능한 모든 액션을 정의하는 파일 하나입니다.

```ts
import { Query } from '@comwit/state'

export type Post = { id: string; title: string /* ... */ }

export type PostState = {
  posts: Query<Post[]> // client-fetched list
  current: Post | null // SSR-hydrated detail
}

export type PostActions = {
  /** @description Toggle like. Optimistic on list + current */
  like(postId: string): Promise<void>
  /** @description Create a new post, redirect on success */
  create(title: string): Promise<void>
}
```

이 파일을 읽으면 도메인 전체를 이해할 수 있습니다. 모든 필드에는 타입이 있고 모든 액션에는 설명이 있습니다. 이것이 계약입니다.

<a id="modelts--list-and-detail-together"></a>

### model.ts — 목록과 상세를 함께

모델은 목록과 현재 항목을 한곳에 보관합니다.

```ts
import { model, query } from '@comwit/state'

export const post = model<PostState>({
  posts: query<Post[]>({
    initialData: [],
    queryFn: () => api.post.findAll(),
  }),
  current: null,
})
```

좋아요 액션이 실행되면 같은 작업 안에서 `this.model.posts.data`와 `this.model.current`를 갱신할 수 있습니다. 이벤트 버스, 수동 동기화, 누락된 갱신이 없습니다.

<a id="actions--stateful-and-self-contained"></a>

### actions/ — 상태를 알고 독립적으로 동작

액션은 UI에서 ID를 인수로 받지 않습니다. 필요한 것을 상태에서 결정합니다.

```ts
import { action, OnError, OnSuccess } from '@comwit/state'
import { user } from '@/state/user/model'

export const postActions = action<Pick<PostActions, 'create'>, AppContext>(({ state, context }) => {
  class PostActions {
    private model = state(post)
    private user = state(user) // cross-domain access

    @OnSuccess(() => context.router.push('/posts'))
    @OnError((e) => toast.error(e instanceof Error ? e.message : 'Failed'))
    async create(title: string) {
      if (!this.user.me) return
      const created = await api.post.create({
        userId: this.user.me.id,
        title,
      })
      this.model.posts.data.push(created)
    }
  }
  return new PostActions()
})
```

`state(user)`를 보세요. 게시물 액션이 사용자 도메인에서 인증 상태를 바로 읽습니다. 속성 전달, 미들웨어, 이벤트 시스템 없이 `this.user.me`만 사용합니다.

액션은 독립적입니다. 인증 확인, API 호출, 상태 갱신, 성공 후 이동, 오류 처리가 모두 한곳에 있습니다. 게시물 좋아요 작업이 파일 네 개로 나뉘지 않습니다.

<a id="indexts--the-clean-export"></a>

### index.ts — 간결한 내보내기

훅은 모델과 액션을 연결합니다.

```ts
import { create } from '@comwit/state'

export const usePost = create<PostState, PostActions>(post, {
  actions: [postActions],
})
```

<a id="ui-just-consumes"></a>

### UI는 사용하기만 합니다

컴포넌트는 필요한 것을 선택하고 렌더링합니다. 그게 전부입니다.

```tsx
const { posts, actions } = usePost((s) => ({
  posts: s.posts,
  actions: s.actions,
}))

if (posts.isLoading) return <Skeleton />
return posts.data.map((p) => <PostCard key={p.id} post={p} />)
```

포맷 로직, 파생 상태, 비즈니스 규칙이 없습니다. 컴포넌트는 도메인 상태의 순수 함수입니다.

<a id="why-this-is-a-big-deal-for-ai"></a>

## AI에게 중요한 이유

모든 원칙이 여기서 연결됩니다.

LLM에게 게시물 북마크 기능을 추가해 달라고 하면 먼저 코드베이스를 이해해야 합니다. 일반적인 React 프로젝트에서 LLM은 게시물 동작을 파악하려고 `components/`, `hooks/`, `api/`, `store/slices/`, `utils/`를 두루 읽어야 합니다. 일부를 놓치고, 잘못된 위치에 코드를 넣고, 일관성을 깨뜨립니다.

comwit의 도메인 구조에서는 LLM이 `state/post/types.ts`를 읽으면 즉시 다음을 알 수 있습니다.

- post 도메인이 관리하는 데이터
- 사용 가능한 액션
- JSDoc이 설명하는 각 액션의 역할
- 모든 상태의 구조

전체 계약이 파일 하나에 있습니다. 그다음 `model.ts`가 초기화를, `actions/*.ts`가 구현을, `index.ts`가 공개 API를 보여줍니다. LLM은 어떤 파일을 수정할지 정확히 압니다.

comwit이 `.ai.md` 파일 하나로 동작하는 이유입니다. 구조 자체가 문서입니다. 관례가 일관되어 LLM이 도메인 하나를 이해하면 별도 안내 없이 다음 도메인도 올바르게 만들 수 있습니다.

작성 순서는 항상 `types.ts` → `model.ts` → `actions/*.ts` → `index.ts`입니다. 의존성 흐름은 항상 pages → state → API입니다. 패턴도 같습니다. 상태는 `model()`, 로직은 `action()`, 훅은 `create()`, 도메인 간 접근은 `state()`입니다.

<a id="good-architecture-was-always-the-answer"></a>

## 좋은 아키텍처는 언제나 답이었습니다

도메인 주도 설계는 수십 년 전부터 존재했고 수직 슬라이스도 여러 해 동안 주목받았습니다. AI가 발명한 것은 아닙니다.

다만 AI는 잘못된 아키텍처의 비용을 무시할 수 없게 만들었습니다.

사람은 복잡한 코드베이스에서 기억, 팀에 전해지는 지식, 직감으로 부족한 구조를 보완합니다. LLM에는 그런 것이 없습니다. 제공한 파일 내용과 지침이 전부입니다. 파일 구조만으로 도메인 경계가 명확하지 않다면 LLM도 어려움을 겪고 다음에 합류할 사람도 마찬가지입니다.

comwit은 이를 염두에 두고 만들었습니다. LLM이 이해하기 쉬운 코드는 누구나 이해하기 쉽습니다. 명확한 파일 관례, 타입이 지정된 계약, 단방향 의존성을 갖춘 도메인 주도 아키텍처는 바이브 코딩에만 좋은 것이 아닙니다.

그냥 좋은 코드입니다. AI 시대가 이를 바꾸지는 않았습니다. 무시하는 비용이 훨씬 커졌을 뿐입니다.
