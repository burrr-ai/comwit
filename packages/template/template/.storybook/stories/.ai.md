# Storybook — 페이지 단위 화면 확인

화면 작업 전에 `src/services/design.md`와 이 문서를 읽는다.
실행: `pnpm storybook` → http://localhost:6006
전용 검사: `pnpm validate:storybook`
정적 빌드: `pnpm build-storybook` → `storybook-static/`

**실제 서비스 검사와 분리한다.** `.storybook/`는 서비스용 TypeScript·lint 대상에서 제외한다.
mock 누락·타입 불일치·미구현은 Storybook 전용 검사/빌드에서만 실패해야 하며,
`pnpm run validate`와 실제 Next.js 서비스 빌드를 막아서는 안 된다.
서비스 코드가 `.storybook/`를 import하거나 서비스 검사에 mock 검사를 연결하지 않는다.
`build-storybook`은 전용 타입·lint·경계 검사 후 Storybook 번들을 검증한다.

## 사이드바 구조

최상위는 **디자인 시스템**, 그다음 **사용자 유형**이다.
`preview.tsx`의 정렬에서 디자인 시스템은 항상 맨 위에 둔다.

```text
디자인 시스템
사용자
  홈
    기본
어드민
  사용자 관리
    기본
  내 계정
    기본
    비밀번호 확인 오류
  로그인
    기본
```

- 서비스 페이지의 title은 `{사용자 유형}/{페이지명}`이다. 사용자 유형은
  서비스(app → 사용자, admin → 어드민)에 대응하며 실제 다른 역할이 생기면 추가한다.
- **모든 스토리는 페이지 단위**다. 버튼·카드·섹션·레이아웃 단독 스토리를 만들지 않는다.
- 디자인 시스템도 토큰·타입·공통 컨트롤을 모은 전체 페이지로 보여준다.
  구성 요소를 추가하면 `stories/design-system/overview.stories.tsx`를 확장한다.
- 같은 페이지의 기본·로딩·빈 목록·오류·권한·완료 상태는 같은 파일의 named export로 만든다.
  해당 화면에 실제로 존재하는 상태만 추가하고, 디자인 샘플을 위해 가짜 기능을 만들지 않는다.
- 모바일/데스크톱은 같은 페이지를 크기만 바꿔 확인한다. 사용자 유형으로 분리하지 않는다.

## 실제 화면 재사용

- 스토리는 `.storybook/stories/{service}/{page}.stories.tsx`에 둔다.
- `src/services/{service}/page/`의 실제 페이지를 import한다. 스토리 전용으로 화면 JSX를 복제하지 않는다.
- 전역 decorator는 실제 `RootLayoutClient`(StateProvider, OverlayProvider, Toaster)를 쓴다.
  story ID가 바뀌면 provider를 다시 마운트해 이전 상태가 새 스토리로 새지 않게 한다.
- 공통 `shell.tsx` decorator에서 **실제 서비스 클라이언트 레이아웃**을 적용한다.
  새 사용자 유형은 이 매핑을 확장하고 페이지별 중첩 레이아웃은 해당 story decorator에 추가한다.
  헤더·사이드바·탭·푸터도 실제 페이지와 같아야 한다. 빈 껍데기를 따로 구현하지 않는다.
- meta에 `app-home`, `admin-account`처럼 안정적인 영문 `id`를 지정해 한글 제목 변경에도 링크를 유지한다.
- `nextjs.navigation.pathname`은 실제 경로로 지정한다. 어드민은 `adminRoutes`를 쓴다.
- `src/app/layout.tsx`나 async 서비스 레이아웃은 import하지 않는다.
  서버가 해 주는 인증 조회 대신 client layout에 고정 `initialUser` fixture를 넣는다.
  로그인 화면은 `initialUser={null}`이다. 라우트의 서버 인증 가드를 변경하지 않는다.
- Storybook은 검토 환경이다. Next 라우팅·인증·서버 통합 검증은 실제 앱에서 별도로 한다.

## Mock 경계 — API만 교체

```text
실제 페이지 + 실제 레이아웃 → 실제 state/query/action → API mock
                                                     ✕ 실제 서버·repository·DB
```

- **교체 지점은 `src/services/{service}/api/{domain}/index.ts`의 공개 API 객체다.**
  `.storybook/mocks/api/{service}-{domain}.ts`를 만들면 `main.ts`의 `api-mocks.mjs`가
  alias·상대·절대 경로 import를 그 파일로 치환한다. API mock 누락, API 내부 파일 또는
  `src/server/`의 runtime import는 빌드를 실패시킨다. 원본으로 fallback하지 않는다.
- mock은 실제 API와 같은 export 이름·인자·응답 타입을 유지한다. `import type`과
  `satisfies DomainAPI`로 계약을 확인하고 `storybook/test`의 `fn`으로 호출을 검증한다.
  실제 모듈을 runtime import하거나 일부 메서드만 원본으로 넘기지 않는다.
  기본 예시는 `mocks/api/app-user.ts`, `mocks/api/admin-user.ts`다.
- **state hook·query·action·페이지·레이아웃은 mock하지 않는다.** 스토리에서 store를
  `.set()`/`.hydrate()`하거나 `isLoading`·`isError`·`data`를 직접 넣어 화면 상태를 만들지 않는다.
  유일한 서버 렌더링 어댑터는 실제 client layout의 `initialUser` 입력이다. 실제 layout이
  원래 하던 hydrate를 수행하게 하고, `mocks/session.ts`의 동일 fixture를 `getMe` 응답에도 쓴다.
- 실제 앱의 개발용 데이터는 기존대로 repository의 `_data/`에 둔다. **Storybook fixture는
  별개로 `.storybook/mocks/`에 둔다.** 실제 repository를 불러와 브라우저에서 실행하지 않는다.
  실제 페이지에 Storybook 분기, `isStorybook`, 스토리 전용 데이터 props를 추가하지 않는다.
- 인증·업로드·외부 HTTP client가 생기면 그 외부 호출 경계도 브라우저 mock으로 교체한다.
  현재 resolver는 미등록 `src/lib/auth-client`를 거부한다. 연결 시 명시적인 치환을 추가하고,
  HTTP API는 MSW 같은 요청 mock으로 처리한다. 실제 서버 액션·DB·외부 인증을 호출하지 않는다.

## 페이지 상태와 상호작용

| 페이지 상태 | 재현 방법 |
|---|---|
| 기본 / 많은 데이터 | 실제 응답 형식의 고정 fixture를 API에서 반환 |
| 로딩 | 조회 API의 Promise를 pending으로 유지해 실제 query가 로딩 표시 |
| 빈 목록 | 빈 `items`와 일치하는 `total`·`totalPages`를 반환 |
| 실패 / 권한 오류 | 실제 API 계약에 맞는 reject 또는 오류 응답 반환 |
| 검색 / 필터 / 페이지 이동 | API 인자에 맞는 응답 반환, `play`에서 UI 조작과 호출 인자·결과 확인 |
| 저장 / 삭제 / 재조회 | API mock의 메모리 fixture를 갱신하고 실제 action의 후속 조회를 거침 |
| 폼 검증 / 모달 열기 | `play`에서 실제 입력·클릭으로 진입하고 결과 assert |

- 같은 페이지의 상태는 `{사용자 유형}/{페이지명}` 아래 named export로 둔다.
  별도 `로딩/…`, `에러/…`, `모바일/…` 최상위 그룹을 만들지 않는다.
- 응답은 페이지네이션·합계·표시 라벨까지 실제 API 계약과 일치해야 한다.
  화면/state에서 fixture를 가공해서 결과를 맞추지 않는다. 날짜·ID는 고정값을 쓴다.
- 각 API mock의 기본 구현·호출 기록·변경 가능한 fixture를 `preview.tsx`의 `beforeEach`에서
  초기화한다. 개별 story의 `beforeEach`에서 그 상태에 필요한 응답만 덮는다.
  새 API mock을 만들면 이 초기화에도 등록한다. state 격리는 실제 provider의 재마운트로 처리한다.
- `play`는 응답·렌더링을 기다리고 `expect`로 결과를 확인한다. 임의 sleep은 사용하지 않는다.
  사용자 조작으로 만드는 폼 검증 예시는 `stories/admin/account.stories.tsx`다.
- 현재 템플릿의 사용자 관리 샘플은 아직 페이지 내부 예시 데이터를 쓰고, 인증 액션도
  연동 전 stub이다. 해당 화면의 데이터/API를 구현할 때 위 경계로 옮긴다.
  아직 없는 API에 맞춰 가짜 로딩·오류 스토리를 추가하거나 통합 검증이 끝났다고 표시하지 않는다.
- 전역 CSS와 로컬 Pretendard를 공유한다. Storybook용으로 브랜드·토큰을 복제하지 않는다.

## 디자인 확인 경로

- 디자인 확인은 Storybook에서 한다. `/design` 앱 라우트를 만들거나 되살리지 않는다.
- 디자인 방향의 기준 문서는 `src/services/design.md`, 실제 토큰은 `src/app/globals.css`다.
- 페이지나 상태를 추가/변경하면 해당 페이지 스토리도 갱신한다.
- 서비스 코드는 `pnpm validate`, Storybook은 `pnpm build-storybook`으로 각각 확인하고
  브라우저에서 레이아웃과 상태를 확인한다. Storybook 실패를 서비스 검사 실패로 합치지 않는다.
