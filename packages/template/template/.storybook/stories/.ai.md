# Storybook: Page-Level Screen Review

Read `src/services/design.md` and this document before working on screens.
Run: `pnpm storybook` → http://localhost:6006
Dedicated checks: `pnpm validate:storybook`
Static build: `pnpm build-storybook` → `storybook-static/`

**Keep Storybook checks separate from the service.** Exclude `.storybook/` from service TypeScript and lint checks. Missing, incompatible, or unfinished mocks must fail only Storybook checks/builds, never `pnpm run validate` or the Next.js service build. Service code must not import `.storybook/` or attach mock checks to service validation. `build-storybook` checks types, lint, and boundaries before validating the bundle.

## Sidebar structure

The top level contains **Design system**, followed by **user types**. Keep Design system first in the `preview.tsx` sort order. Existing localized labels follow this structure:

```text
Design system
User
  Home
    Default
Admin
  User management
    Default
  My account
    Default
    Password confirmation error
  Sign in
    Default
```

- Service-page titles follow `{user type}/{page name}`. User types correspond to services (`app` → User, `admin` → Admin); add one only for a real new role.
- **Every story represents a page.** Do not create standalone button, card, section, or layout stories.
- The design system is also a full page combining tokens, typography, and shared controls. Extend `stories/design-system/overview.stories.tsx` when adding components.
- Put default, loading, empty, error, permission, and complete states for one page in named exports in the same file. Include only states that actually exist; do not invent features for design samples.
- Check mobile/desktop by resizing the same page, not by creating user types.

## Reuse real screens

- Place stories in `.storybook/stories/{service}/{page}.stories.tsx`.
- Import real pages from `src/services/{service}/page/`; never duplicate page JSX for stories.
- The global decorator uses the real `RootLayoutClient` with StateProvider, OverlayProvider, and Toaster. Remount providers when the story ID changes to isolate state.
- The shared `shell.tsx` decorator uses the **real service client layout**. Extend its mapping for a new user type and add nested page layouts to the story decorator. Headers, sidebars, tabs, and footers must match the real screen; do not build empty substitutes.
- Set stable English meta IDs, such as `app-home` or `admin-account`, so localized title changes preserve links.
- Set `nextjs.navigation.pathname` to the real path; use `adminRoutes` for admin pages.
- Do not import `src/app/layout.tsx` or async service layouts. Pass a fixed `initialUser` fixture to the client layout instead of server authentication reads. Sign-in screens use `initialUser={null}`. Do not change server authentication guards.
- Storybook is a review environment. Verify Next routing, authentication, and server integration separately in the real app.

## Mock only the API boundary

```text
Real page + real layout → real state/query/action → API mock
                                                   ✕ real server/repository/DB
```

- **Replace the public API object from `src/services/{service}/api/{domain}/index.ts`.** Create `.storybook/mocks/api/{service}-{domain}.ts`; `main.ts` uses `api-mocks.mjs` to redirect alias, relative, and absolute imports. Missing mocks, API internal imports, and runtime imports from `src/server/` fail the build, with no fallback to real implementations.
- Match the real API's export names, arguments, and response types. Check contracts with `import type` and `satisfies DomainAPI`, and calls with `fn` from `storybook/test`. Never import real modules at runtime or forward selected methods to the real API. See `mocks/api/app-user.ts` and `mocks/api/admin-user.ts`.
- **Do not mock state hooks, queries, actions, pages, or layouts.** Do not construct screen state with store `.set()`/`.hydrate()` or direct `isLoading`, `isError`, or `data` assignments. The only server-render adapter is the real client layout's `initialUser` input. Let that layout hydrate normally and reuse the same `mocks/session.ts` fixture in `getMe` responses.
- Real development data stays in repository `_data/`. **Storybook fixtures belong separately in `.storybook/mocks/`.** Never import the real repository into the browser. Do not add Storybook branches, `isStorybook`, or story-only data props to real pages.
- Mock external authentication, upload, and HTTP-client boundaries when introduced. The resolver currently rejects unregistered `src/lib/auth-client`; add explicit replacements during integration. Use request mocks such as MSW for HTTP APIs. Never call real server actions, databases, or external authentication.

## Page states and interactions

| State | How to reproduce |
|---|---|
| Default / many records | Return a fixed API fixture matching the response contract |
| Loading | Keep the query API Promise pending so the real query shows loading |
| Empty | Return empty `items` and matching `total`/`totalPages` |
| Failure / permission error | Reject or return an error according to the real API contract |
| Search / filters / pagination | Respond to API arguments; use `play` to interact and verify calls/results |
| Save / delete / refetch | Update the API mock's in-memory fixture, then run the real action's follow-up query |
| Form validation / dialog opening | Use real input/clicks in `play` and assert the result |

- Keep states as named exports under `{user type}/{page name}`. Do not create separate top-level Loading, Error, or Mobile groups.
- Responses must match pagination, totals, and display labels in the real contract. Do not transform fixtures in screens/state to force the expected result. Use fixed dates and IDs.
- Reset mock implementations, call histories, and mutable fixtures in `preview.tsx` `beforeEach`. Each story overrides only what its state needs. Register new API mocks in the reset. Real provider remounts isolate state.
- In `play`, wait for responses/rendering and verify with `expect`; no arbitrary sleeps. See `stories/admin/account.stories.tsx` for user-triggered form validation.
- The current user-management example still has page-local sample data and pre-integration authentication stubs. Move it to these boundaries when implementing its data/API. Do not invent loading/error stories for nonexistent APIs or claim integration has been verified.
- Share global CSS and local Pretendard. Do not duplicate branding/tokens for Storybook.

## Design review

- Review designs in Storybook; never create or restore a `/design` app route.
- `src/services/design.md` defines design direction; `src/app/globals.css` holds actual tokens.
- Update the relevant page story whenever a page or state changes.
- Check service code with `pnpm validate` and Storybook separately with `pnpm build-storybook`, then inspect layout and states in the browser. Do not merge Storybook failures into service validation failures.
