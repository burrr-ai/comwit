# Admin Service

An admin-only service. It has a login/dashboard separate from regular users (app).

## Routes

The app-router filesystem stays under the internal `/admin` path. Users enter
through the project-specific public path in `ADMIN_BASE_PATH` from
`src/lib/admin-routes.ts`. The template default is `/관리자`.
`src/proxy.ts` rewrites the public root and every nested path to `/admin`,
including `/login`, `/members`, and `/api/auth/*`. It returns an explicit,
non-cacheable 404 for direct `/admin` and `/admin/*` requests before rewriting.
Authentication and authorization still belong in the server layout and APIs.

Keep this mapping in the request proxy, before filesystem/dynamic route matching.
Do not reintroduce admin `afterFiles` rewrites in `next.config.ts`: a hosted
runtime can resolve an app catch-all before applying those rules to RSC
navigation/prefetch. A working root or a 200 HTML response alone does not prove
that nested navigation works. Decode only prefix segments for comparison;
preserve the encoded suffix and query when cloning `request.nextUrl`, and use
`NextResponse.rewrite` so POST bodies and the public browser URL are retained.
Keep both public admin pages/auth and internal `/admin/api/auth` in the matcher.

| Route helper | Purpose |
|------|------|
| `adminRoutes.dashboard` | Dashboard (login required) |
| `adminRoutes.login` | Admin login |
| `adminRoutes.account` | Current administrator account and password change (login required) |

- Never hardcode a user-facing admin URL. Import `adminRoutes` in code.
- Do not rename `src/app/(admin)/admin`; that is the stable internal route.
- Browser-side auth uses `ADMIN_AUTH_BASE_PATH`. Better Auth's server instance
  uses `INTERNAL_ADMIN_AUTH_BASE_PATH`, and the admin auth route normalizes the
  public request URL before passing it to Better Auth. Follow the `auth-setup`
  skill instead of wiring these paths manually.

## One-time path initialization

Before the first task that creates, enables, or connects authentication to an
admin screen, read `ADMIN_BASE_PATH`. If it is still exactly `/관리자`, use the
public path explicitly requested by the user. If the user did not choose one,
generate a project-specific path with a non-secret random suffix, for example:

```bash
node -e "console.log('/관리자-' + require('crypto').randomBytes(5).toString('hex'))"
```

Normalize a chosen path to one leading slash and no trailing slash. Do not use
`/admin`, `/api`, a Next.js asset prefix, or another existing application route.
Edit only the `ADMIN_BASE_PATH` assignment. The derived public auth path changes
with it; do not rename the internal route or change either `INTERNAL_*` constant.
The public path reduces generic scanner noise but is not an authentication
secret. After changing it, use the guidance below to tell the user the actual
entry URL.

## User entry guidance (required)

When the admin screen first becomes usable, admin authentication is completed,
or `ADMIN_BASE_PATH` changes, read the actual value from
`src/lib/admin-routes.ts` and tell the user in chat:

> 관리자 화면이 준비됐어요.
> - 지금 확인: `http://localhost:3000{ADMIN_BASE_PATH}`
> - 배포 후: `https://배포도메인{ADMIN_BASE_PATH}`
>
> 이 주소는 이 프로젝트의 전용 관리자 주소예요. 바로 열 수 있도록
> 북마크해두세요. 잊어버리면 다시 물어보셔도 같은 주소를 알려드릴게요.

If the deployment domain is known, print the complete deployed URL instead of
the placeholder. The user cannot inspect files, so never ask them to find the
path themselves. If no administrator account exists, do not expose or create a
sign-up route. Tell the user that they can explicitly ask the AI to set a desired
login ID (email) and password. Never choose or print credentials on their behalf.

## Administrator account rules (important)

### 1. Public admin sign-up is forbidden
- Do not create an admin sign-up page, route, link, or call to `authClient.signUp`.
- Better Auth admin configuration must set `emailAndPassword.disableSignUp: true`
  so removing the screen cannot leave a callable public sign-up API behind.
- The login screen contains only login. Do not add a "create account" link.

### 2. Initial credentials are created only on an explicit chat request
- When the user explicitly provides the desired administrator login ID (email)
  and password, create the account through Better Auth's server-only admin API.
- Never add a temporary public bootstrap/sign-up endpoint. Do not log, echo, or
  persist the requested password in source or tracked files.
- If the user has not explicitly requested credentials, leave account creation
  undone and explain that they can ask the AI to set them later.

### 3. Password change stays available after login
- Keep `adminRoutes.account` inside the authenticated admin area and link it from
  the admin navigation as "내 계정".
- The page must require the current password, a new password, and confirmation.
- Wire it to Better Auth `changePassword` during `auth-setup` and revoke other
  sessions after a successful change.

## Layer rules

- `services/admin/api/` · `state/` · `page/` follow the rules in `services/.ai.md`, `api.ai.md`, `state.ai.md`, `page.ai.md` as-is.
- Do not mix admin-only state (`useAdminUser`, etc.) with the `app` service. No cross-imports.
- The auth guard is performed in the server layout at `services/admin/page/layout/` (not in the request proxy).

## Checklist when building admin screens

- [ ] Is the app-router file under the internal `/admin/*` route?
- [ ] Do all user-facing links use `adminRoutes` rather than a hardcoded path?
- [ ] Does browser auth use `ADMIN_AUTH_BASE_PATH` while the Better Auth server uses `INTERNAL_ADMIN_AUTH_BASE_PATH`?
- [ ] Does `src/proxy.ts` rewrite the root, nested pages, and auth API while preserving the suffix/query?
- [ ] On both local and deployed builds, do direct entry, refresh, and Link/RSC navigation reach the correct admin page (not merely HTTP 200)?
- [ ] Do direct `/admin` and `/admin/*` requests return 404, including auth API requests?
- [ ] Is it a page that requires login → check the session guard in the layout
- [ ] Are the admin sign-up page, link, state action, and public API all absent/disabled?
- [ ] Is `adminRoutes.account` protected and reachable from the admin navigation?
- [ ] Does password change verify the current password and revoke other sessions?
- [ ] Did you add the new menu to `navGroups` in `page/layout/content.tsx`?
- [ ] When admin first became usable, did you give the user the actual local/deployed admin URL?
